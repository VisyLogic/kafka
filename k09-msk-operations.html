K09 · Move from a lab broker to MSK and EKS

Amazon MSK manages Kafka broker infrastructure; producers and consumers still use Kafka protocols and group semantics. AWS CLI creates/describes a cluster but Kafka clients create/read/write topics through the data plane. EKS runs the Java clients. A bootstrap endpoint is the starting address, after which broker metadata advertises further endpoints that must also resolve and be reachable.

When to use it

  • Operate Kafka in private AWS networking with IAM-authenticated Java clients.
  • Diagnose DNS, routes, security groups, TLS and permission failures separately.
  • Monitor lag, processing rate, failures, broker storage and in-sync replicas.

Create through the AWS console / IDE

  1. Complete main lessons 02 IAM, 03 networking, 07 MSK, 12 EKS and 13 pod identity. Use their Console and CLI steps to create infrastructure rather than duplicating a cluster.
  2. Inspect IAM bootstrap brokers and private routes. EventFlow’s AWS profile uses SASL_SSL plus AWS_MSK_IAM; local plaintext settings are not production security settings.
  3. Give the application pod scoped Kafka permissions and the IAM client library. KEDA has its own identity/permissions; it does not inherit the activity pod role.
  4. Run the Java KafkaProbe from an authorized pod to test the actual broker data plane. Creating a cluster successfully does not demonstrate produce/consume connectivity.
  5. Inspect per-partition group lag and worker throughput before tuning. Report retained-topic offset positions separately from current loan counts; offset sums are not a reliable count of retained records after retention, compaction or gaps.

Create or inspect through CLI

Choose this as an alternative provisioning path; do not create duplicate named resources. Commands are examples for a sandbox and require replacing placeholders. CloudShell examples use Bash; Windows-specific commands are labelled.
Command / example
# AWS CLI: control-plane inspection, using your sandbox identity.
aws kafka list-clusters-v2
aws kafka get-bootstrap-brokers --cluster-arn YOUR_CLUSTER_ARN
# Authorized VPC-connected client inside EKS; replace pod name.
kubectl -n eventflow exec YOUR_CONSOLE_POD -- java -cp /app/eventflow.jar com.eventflow.tools.KafkaProbe
kubectl -n eventflow logs deployment/eventflow-activity --tail=100
# Local integration logs, separate environment:
docker compose logs --tail 100 adapter sourcing activity

Test this component before continuing

Demonstrate an authorized produce/consume probe, then inspect a deliberately denied permission in a disposable sandbox. Record whether failure occurred during DNS, TCP, TLS, authentication, authorization or processing.

Exit criterion

You can explain the MSK control plane versus Kafka data plane, validate private connectivity and identify which runtime identity needs which permission. Actual AWS execution remains a learner exercise.

Explain and investigate

The bootstrap connection works but publishing times out. What advertised broker addresses, routes, security groups and topic permissions should you check before increasing timeouts?

What to record in your lab notebook
  • Account/region, resource IDs and chosen provisioning method.
  • Relevant configuration and why you chose it.
  • The command/test and the observed result, including failures.
  • Recovery action and how you checked the business invariants.
  • Known gaps and the next experiment; exclude secrets and task tokens.
