19 · Infrastructure as code and enterprise delivery

After the console labs, rebuild the environment reproducibly from reviewed CloudFormation in a separate account/region or using a deliberate import plan. Do not deploy a stack over unmanaged resources with identical names and assume CloudFormation will adopt them.

When to use it

  • Reviewable infrastructure, predictable environment promotion, drift detection and rollback.
  • Build once, test, scan, sign/attest as required, and deploy the same image digest.
  • Use short-lived CI OIDC roles and environment approvals rather than access-key secrets.

Create through the AWS console / IDE

  1. CloudFormation → Create stack: network, core and platform are separate deployment units. Review the change set and IAM changes before executing.
  2. Record stack outputs as deployment inputs. Separate business configuration versions from image versions and infrastructure versions.
  3. After manual learning, use separate dev/test/prod accounts, repository reviews, automated tests, scoped deployment roles and explicit production gates.
  4. Refactor the shared teaching pod role into workload-specific roles and service accounts. Add KMS/Secrets Manager only when the actual encryption or external-credential need requires them.
  5. Configure deletion protection/retention and backup restore exercises for financial data. Use CloudFormation drift detection to identify console changes that would otherwise disappear in the next release.

Create or inspect through CLI

Choose this as an alternative provisioning path; do not create duplicate named resources. Commands are examples for a sandbox and require replacing placeholders. CloudShell examples use Bash; Windows-specific commands are labelled.
Command / example
aws cloudformation validate-template --template-body file://infrastructure/cloudformation/core.yaml
aws cloudformation deploy --stack-name eventflow-core --template-file infrastructure/cloudformation/core.yaml --capabilities CAPABILITY_IAM --parameter-overrides ArtifactBucketName=YOUR_UNIQUE_BUCKET --no-execute-changeset
aws cloudformation list-change-sets --stack-name eventflow-core
# Review the change-set ID, then explicitly execute it.
aws cloudformation execute-change-set --stack-name eventflow-core --change-set-name CHANGE_SET_NAME
aws cloudformation detect-stack-drift --stack-name eventflow-core
# Code rollout is separate:
kubectl -n eventflow set image deployment/eventflow-activity activity=YOUR_REPOSITORY@sha256:YOUR_DIGEST
kubectl -n eventflow rollout status deployment/eventflow-activity

Test this component before continuing

Review a harmless change set and detect drift on a disposable lab setting. In test, deploy a known image digest and practice rollout undo. Recheck accounting invariants after rollback rather than assuming Kubernetes rollback undoes posted financial results.

Exit criterion

An auditable release with source commit, test evidence, image digest, business-rule version and infrastructure change set. No automated AWS deployment is performed by reading this course.

Explain and investigate

A bad calculation was deployed and posted. Why is rolling back the container insufficient? Design an explicit reversal/rebook process rather than editing historical results.

What to record in your lab notebook
  • Account/region, resource IDs and chosen provisioning method.
  • Relevant configuration and why you chose it.
  • The command/test and the observed result, including failures.
  • Recovery action and how you checked the business invariants.
  • Known gaps and the next experiment; exclude secrets and task tokens.
