13 · Pod identity, configuration and service-by-service rollout

The image is generic; environment configuration selects AWS endpoints, broker security and SERVICE_ROLE. LocalStack uses dummy local credentials only with an explicit local endpoint. AWS uses the default credential chain and EKS Pod Identity. Separate business configuration from connection and release configuration.

When to use it

  • Workload credentials without stored access keys.
  • Declarative rollouts, readiness probes, resource limits and stable discovery.
  • The teaching manifests use one service account; the enterprise hardening lab assigns one role/service account per workload.

Create through the AWS console / IDE

  1. EKS → cluster → Add-ons → Get more add-ons → EKS Pod Identity Agent. Install it and verify its daemon pods are healthy.
  2. EKS → Access → Pod Identity associations → Create. Associate namespace eventflow and service account eventflow with EventFlowApplicationRole.
  3. Copy workloads.yaml to a deployment-specific file. Replace all image references with the ECR digest. Set AWS_ENDPOINT_URL empty, the real account/region/bucket, IAM brokers, SASL_SSL and AWS_MSK_IAM.
  4. Create namespace/config/service account, then deploy mock-source first, followed by activity, sourcing, adapter, and finally console. The console owns the single coordinator.
  5. Keep the console Service private and use kubectl port-forward for learning. Add authentication before considering a public endpoint.

Create or inspect through CLI

Choose this as an alternative provisioning path; do not create duplicate named resources. Commands are examples for a sandbox and require replacing placeholders. CloudShell examples use Bash; Windows-specific commands are labelled.
Command / example
aws eks create-addon --cluster-name eventflow --addon-name eks-pod-identity-agent
aws eks create-pod-identity-association --cluster-name eventflow --namespace eventflow --service-account eventflow --role-arn APPLICATION_ROLE_ARN
# After replacing all deployment-specific values:
kubectl apply -f YOUR_CONFIGURED_WORKLOADS.yaml
kubectl -n eventflow rollout status deployment/eventflow-mock-source
kubectl -n eventflow rollout status deployment/eventflow-activity
kubectl -n eventflow get pods
kubectl -n eventflow logs deployment/eventflow-sourcing --tail=30
kubectl -n eventflow port-forward service/eventflow-console 8095:8095

Test this component before continuing

Use logs to confirm each role starts, then run KafkaProbe inside the console pod. Verify configuration was seeded in DynamoDB using seed-aws.py before startup. Check that no AWS_ACCESS_KEY_ID/SECRET_ACCESS_KEY is present in the pod spec.

Exit criterion

Ready Java roles, private discovery of eventflow-mock-source:9095, successful SDK calls through pod identity, and a console reached only through the local port-forward.
