16 · Assemble the application and run the capstone

The services are now tested individually. Assemble them without changing the data contracts. The acceptance check follows one business request across Kafka, SQS, batch manifest, workflow, gRPC source, loan topic, accounting transaction and reconciliation.

When to use it

  • Cross-service integration testing and release acceptance.
  • A repeatable golden scenario with known expected outputs.
  • Business reconciliation is more useful than checking only HTTP 200 or a green pod.

Create through the AWS console / IDE

  1. Verify the resource names and frozen configuration match the application. Seed application/fixtures/default-config.json using scripts/seed-aws.py in AWS or bootstrap.py locally.
  2. Check all roles are Ready and the GUI reports the expected broker mode. A test must not accidentally point at LocalStack while you believe it is AWS.
  3. Run a 100-loan POOL settled request. With eventBatchSize 1000, a max-wait timer or manual flush starts the small batch.
  4. Inspect one event, the workflow history, one source checkpoint, and the first loan/application JSON results.
  5. Run 100 LOAN events as a second test. Confirm the loan workflow rather than the pool workflow was executed.

Create or inspect through CLI

Choose this as an alternative provisioning path; do not create duplicate named resources. Commands are examples for a sandbox and require replacing placeholders. CloudShell examples use Bash; Windows-specific commands are labelled.

Test this component before continuing

Compare distinct loans, loan/application outcomes, BE/AR counts, debit/credit balance, workflow SUCCEEDED, source cursor and Kafka lag. Save evidence containing IDs and counts, never credentials or task tokens.

Exit criterion

Default 100-loan test: 300 unique loan/application items, 900 BEs, 900 ARs and 1800 debit/credit lines. Kafka lag drains to zero and the workflow succeeds. Current local evidence records both POOL and LOAN passing; AWS labs still need to be performed by the learner.

"""Real end-to-end test. Requires the running Docker application; never synthesizes success."""
import argparse,json,time,urllib.request
from urllib.error import URLError
def request(path,data=None):
    body=None if data is None else json.dumps(data).encode()
    req=urllib.request.Request('http://127.0.0.1:8095/api/'+path,data=body,headers={'Content-Type':'application/json'})
    with urllib.request.urlopen(req,timeout=30) as r:return json.load(r)

def verify_database(row,region='us-east-1',endpoint='http://127.0.0.1:4570'):
    import boto3
    from decimal import Decimal
    options={'region_name':region}
    if endpoint:options.update(endpoint_url=endpoint,aws_access_key_id='test',aws_secret_access_key='test')
    db=boto3.client('dynamodb',**options)
    bundles=[]
    for page in db.get_paginator('query').paginate(TableName='eventflow-data',ConsistentRead=True,
        KeyConditionExpression='pk = :p AND begins_with(sk, :s)',
        ExpressionAttributeValues={':p':{'S':'RUN#'+row['runId']},':s':{'S':'RESULT#'}}):
        bundles.extend(json.loads(item['payload']['S']) for item in page['Items'])
    assert len(bundles)==row['totalLoans']*len(row['config']['applications']),len(bundles)
    identities={(b['loanId'],b['application']) for b in bundles}
    assert len(identities)==len(bundles),'Duplicate loan/application result'
    count=0
    for bundle in bundles:
        assert bundle['status']=='COMMITTED',bundle
        for record in bundle['records']:
            assert sum(Decimal(line['debit'])-Decimal(line['credit']) for line in record['AR']['lines'])==0,record
            count+=1
    assert count==row['beCount']==row['arCount'],count
    return {'loanApplicationItems':len(bundles),'balancedAR':count}

def main():
    p=argparse.ArgumentParser();p.add_argument('--level',choices=['POOL','LOAN'],default='POOL');p.add_argument('--timeout',type=int,default=240)
    p.add_argument('--run-id',help='Watch an existing run instead of submitting a new event')
    p.add_argument('--verify-db',action='store_true',help='Also reconcile actual DynamoDB items and debit/credit balance')
    p.add_argument('--aws-native',action='store_true',help='Verify DynamoDB in AWS with the normal credential chain instead of LocalStack')
    p.add_argument('--region',default='us-east-1')
    a=p.parse_args()
    from datetime import date
    run={'runId':a.run_id} if a.run_id else request('runs',{'totalLoans':100,'poolSize':100,'level':a.level,'eventType':'settled','accountingDate':date.today().isoformat()})
    print('Watching' if a.run_id else 'Started',run['runId']);deadline=time.monotonic()+a.timeout
    row={'status':'WAITING_FOR_BACKEND'}
    while time.monotonic()<deadline:
        try:row=request('run?id='+run['runId'])
        except (URLError,TimeoutError):
            # Java-service rebuilds briefly stop HTTP; keep watching the same run.
            time.sleep(3)
            continue
        if row['status']=='COMMITTED':
            apps=row['config']['applications'];expected=sum(len(app['businessEvents']) for app in apps)*row['totalLoans']
            assert row['published']==row['totalLoans'],row
            assert row['beCount']==expected and row['arCount']==expected,row
            detail=verify_database(row,region=a.region,endpoint=None if a.aws_native else 'http://127.0.0.1:4570') if a.verify_db else {}
            print(json.dumps({'status':'PASS','runId':run['runId'],'published':row['published'],'BE':row['beCount'],'AR':row['arCount'],**detail}))
            return
        if row.get('generationError'):raise RuntimeError(row['generationError'])
        time.sleep(3)
    raise TimeoutError('Run did not commit within test deadline: '+json.dumps(row))
if __name__=='__main__':main()

Explain and investigate

A workflow says SUCCEEDED but a downstream GL destination has not received a posting. Which completion contract is missing? This POC ends at DynamoDB; it does not implement a GL delivery guarantee.

What to record in your lab notebook
  • Account/region, resource IDs and chosen provisioning method.
  • Relevant configuration and why you chose it.
  • The command/test and the observed result, including failures.
  • Recovery action and how you checked the business invariants.
  • Known gaps and the next experiment; exclude secrets and task tokens.
