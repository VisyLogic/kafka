M05 · Optional SQS handoff, troubleshooting and cleanup

Complete the hands-on path by bridging enriched Kafka records to a real SQS work queue. This illustrates EventFlow’s adapter pattern; SQS is an optional extension to the MSK exercises, not the name for a Kafka topic. The bridge waits for SQS acceptance before committing Kafka progress, but no atomic transaction spans both systems, so duplicates remain possible after a crash.

When to use it

  • Integrate a retained Kafka stream with AWS-native work delivery.
  • Learn receive/delete acknowledgement and DLQ configuration.
  • Diagnose each boundary and remove only the disposable lab resources.

Create through the AWS console / IDE

  1. If you used the lab CloudFormation stack, the queue and DLQ already exist. Open SQS using QueueUrl from Outputs. Manual path: create a Standard DLQ, then a Standard main queue with server-side encryption, visibility timeout 60 seconds and redrive after three receives; grant the client role SendMessage/ReceiveMessage/DeleteMessage/GetQueueAttributes only for that queue ARN.
  2. Set MSK_SQS_URL on the EC2 client and run bridge 10. It consumes learning.msk.enriched-loans using its own msk-learning-bridge-01 group. Inspect the queue in the SQS Console → Send and receive messages → Poll for messages. Find mockCreditScore=720 in a message body. Polling makes messages temporarily invisible and increases receive counts; do not repeatedly poll just to watch them.
  3. The CLI receive below returns at most ten messages and may return fewer. Record event IDs and delete each message only after inspecting it, using that response’s receipt handle. Empty responses may mean messages are temporarily invisible; a single receive call is not a count reconciliation. The sample itself does not drain SQS.
  4. Troubleshoot: DNS/TCP timeout → VPC routes, NAT/endpoints and SG9098; IAM handshake → role credentials, IAM client dependency and region; topic/group authorization → scoped ARNs; init timeout → broker health; consumption timeout → existing group offsets, missing input or unhealthy ISR; ZIP 404 → publish updated course; SQS AccessDenied → queue policy/role/region. Check EC2 SSM registration and egress before retrying downloads.
  5. Capture the evidence, then delete only msk-learning-lab. Delete a separately created download bucket or manual resources only if you created them for this lab. Delete a dedicated network stack last, after dependents; retained NAT gateways continue to incur charges. Existing EventFlow resources and accounting data are outside this cleanup.

Create or inspect through CLI

Choose this as an alternative provisioning path; do not create duplicate named resources. Commands are examples for a sandbox and require replacing placeholders. CloudShell examples use Bash; Windows-specific commands are labelled.
Command / example
# EC2 terminal: QueueUrl is the lab stack output.
export MSK_SQS_URL='PASTE_QUEUE_URL_HERE'
java -jar target/msk-hands-on.jar bridge 10 msk-learning-bridge-01
# AWS CLI in your authorized operator terminal, same region:
aws sqs receive-message --queue-url YOUR_QUEUE_URL --max-number-of-messages 10 --wait-time-seconds 10 --visibility-timeout 60
# After checking one message, use its current ReceiptHandle:
aws sqs delete-message --queue-url YOUR_QUEUE_URL --receipt-handle YOUR_RECEIPT_HANDLE
# Inspect redrive/visibility configuration:
aws sqs get-queue-attributes --queue-url YOUR_QUEUE_URL --attribute-names All
# After preserving evidence; delete only the disposable lab:
aws cloudformation delete-stack --stack-name msk-learning-lab
aws cloudformation wait stack-delete-complete --stack-name msk-learning-lab

Test this component before continuing

Verify PASS bridge count=10 and inspect ten distinct sample event IDs in SQS across one or more receives. Standard SQS may redeliver duplicates. Check enriched sample values, explain the Kafka commit boundary, and confirm lab resources are gone after cleanup. A DLQ cannot be proven by a single successful receive; use a deliberate separate receive-without-delete drill if desired.

Exit criterion

A small sample has crossed both Kafka topics and an optional SQS boundary, with recorded IDs and clear delivery semantics. You can locate each failure boundary and safely clean up the separate AWS lab. Actual AWS deployment and these service tests must be performed by the learner; they are not pre-certified by the offline build.

# Amazon MSK hands-on sample

Open the offline course's **Amazon MSK hands-on** section for the ordered lessons M01–M05. This is a separate sample application, not a deployment of the full finance pipeline.

```text
Java produce → learning.msk.loan-events
                    ├─ Java consume → terminal
                    └─ Java enrich (mock credit score = 720)
                          → learning.msk.enriched-loans
                               → optional Java bridge → SQS → manual test reader
```

These Kafka topics are the streaming destinations sometimes called “Kafka queues.” SQS is a separate optional service; it is not required between these two topics. Only sample data and enrichment are mocked. MSK, Kafka acknowledgements, consumer groups and SQS calls are real when deployed to AWS.

## Build

Install Java 21 and Maven. From this folder run `mvn -B package`. The executable artifact is `target/msk-hands-on.jar`. No dependency on EventFlow's configuration, databases or LocalStack is required. Credentials use the default AWS provider chain (the EC2 role in the AWS lab); do not put keys in source.

## Run inside the VPC

Use the course's SSM-managed EC2 client. CloudShell's ordinary public environment and an unconnected workstation cannot reach these private brokers. Upload/extract this source folder on that client and build, or copy the built JAR using the documented S3 handoff. Bash:

```bash
export AWS_REGION=us-east-1
export MSK_BOOTSTRAP='PASTE_BootstrapBrokerStringSaslIam_HERE'
java -jar target/msk-hands-on.jar init
java -jar target/msk-hands-on.jar produce 10
java -jar target/msk-hands-on.jar consume 10 msk-learning-reader-01
java -jar target/msk-hands-on.jar enrich 10 msk-learning-enricher-01
java -jar target/msk-hands-on.jar consume-enriched 10 msk-learning-output-reader-01
export MSK_SQS_URL='PASTE_LAB_QUEUE_URL_HERE'
java -jar target/msk-hands-on.jar bridge 10 msk-learning-bridge-01
```

Use new consumer group suffixes to read retained records again. Repeating produce intentionally adds more events. Replaying an enricher/bridge may append duplicate outputs: this sample has no DynamoDB financial idempotency store. Kafka producer idempotence does not make Kafka plus SQS atomic. These are bounded lab processes (default 10 records, two-minute consumption window), not production daemons.

`init` creates three-partition topics with replication factor two and min.insync.replicas two. On a two-broker lab this favors durability and blocks writes if either replica is unavailable; it is not a production availability design. For an isolated local broker only, set `MSK_IAM=false` and `MSK_REPLICAS=1`. Do not use those settings for AWS.

## Infrastructure

`msk-lab.yaml` uses an existing VPC and two private broker subnets in distinct AZs. The client subnet must have outbound NAT connectivity for Session Manager, package installation, Maven and the optional S3 handoff. Alternative private endpoints require the appropriate SSM/S3/SQS and download connectivity. It creates two billable Standard brokers, a small EC2 client, IAM role, security groups and SQS/DLQ. The main course network template can create a disposable VPC/NAT if needed. Review current AWS availability, quotas, costs and the change set before execution. No AWS resources are created by opening HTML or compiling this project.

## Evidence boundary and cleanup

Java compilation/package and local CLI usage validation can be checked without AWS. Actual MSK authentication, network connectivity and SQS delivery must be tested in your AWS sandbox. Preserve lab results, then delete the lab stack and any separately created download bucket/objects; delete a dedicated network stack only after dependents are gone. Existing EventFlow infrastructure is not part of this cleanup.

Explain and investigate

The bridge crashes after SendMessage succeeds and before commitSync. What happens on restart? How would the full finance application prevent duplicate accounting effects without pretending the Kafka/SQS handoff is atomic?

What to record in your lab notebook
  • Account/region, resource IDs and chosen provisioning method.
  • Relevant configuration and why you chose it.
  • The command/test and the observed result, including failures.
  • Recovery action and how you checked the business invariants.
  • Known gaps and the next experiment; exclude secrets and task tokens.
