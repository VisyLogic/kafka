17 · Batching, Kafka lag, KEDA and node capacity

Event batch size, source concurrency, loan envelope size, activity chunking, pod replicas and node capacity are independent controls. A larger event batch generates more loan work, but capacity should follow backlog and bottlenecks rather than allocate one giant in-memory batch.

When to use it

  • Event-driven pod scaling and predictable bounded workers.
  • KEDA scales activity replicas using Kafka envelope lag; source scaling uses pending workflow batches.
  • Node autoscaling supplies capacity for Pending pods. Compose supports only manual replica changes.

Create through the AWS console / IDE

  1. KEDA is installed inside Kubernetes, not through the EKS Create cluster page. Use its official Helm chart and review the selected version.
  2. Apply the activity ScaledObject with reachable broker addresses and the correct security profile. AWS IAM needs SASL OAuth bearer MSK token support and a separately permitted KEDA operator identity.
  3. Apply sourcing-scaling.yaml. One source Activity belongs to one worker; the sourceConcurrency setting creates bounded parallel calls within it. Source pods scale across batches.
  4. Set min/max pods and observe resource requests/limits. Six loan-topic partitions limit useful normal consumer-group parallelism to six.
  5. Install and configure Cluster Autoscaler or Karpenter separately. Setting node-group MaxSize=3 does not itself adjust DesiredSize.

Test this component before continuing

Begin with 1000 loans, then 10000, not 14 million. Record source rate, record/envelope lag, pod count, CPU/memory, database throttling and drain time. Pause new source production and watch consumers drain. Let cooldown scale pods back down.

Exit criterion

Measured scale-up and scale-down in Kubernetes. Docker tests alone do not establish this. KEDA and AWS node autoscaling have not been certified by the current LocalStack smoke tests.

# Requires KEDA installed first. This is real Kubernetes scaling configuration, not Compose simulation.
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: {name: eventflow-activity, namespace: eventflow}
spec:
  scaleTargetRef: {name: eventflow-activity}
  minReplicaCount: 1
  maxReplicaCount: 6
  pollingInterval: 15
  cooldownPeriod: 60
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: REPLACE_WITH_REACHABLE_BROKERS
        consumerGroup: eventflow-activity
        topic: eventflow.enriched-loans
        lagThreshold: '10'
        offsetResetPolicy: earliest
        allowIdleConsumers: 'false'
# For AWS MSK TLS, add authenticationRef and a TriggerAuthentication specifying tls=enable.
# Kafka lag counts envelopes, not loans. Six partitions limit useful concurrent consumers to six.

Explain and investigate

Lag grows while DynamoDB is throttling. Why might adding pods worsen the problem? Propose rate limits and a database-aware ceiling.
